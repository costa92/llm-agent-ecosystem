## Round 2 (adversarial review) — REVISED RESOLUTIONS (supersede §1–§8 where they conflict)
Round 2 found ONE BLOCKER (proven with a scratch test, then removed) and two MAJORs before any code. The Phase-2 `Copy`/`Merge` combinators were stress-tested (diamond ×5 sizes, early-Close, nested Copy root-first AND leaf-first Close while inner broadcaster live mid-send) and are ROCK-SOLID — the blocker is in the EXECUTOR logic the design wraps around them, and §3 step 3's wording papered over it.

- **BLOCKER — sequential subtree materialization at a fan-in DEADLOCKS.** §3 step 3 ("each source subtree is walked") reads naturally as: walk subtree A to its stream, then walk B, then `Merge(A,B)`. When A and B share an upstream Copy, that DEADLOCKS — the broadcaster (combinators.go:114-120) fills A's buf-1 chan and blocks on B's chan before B's puller exists; A drains empty; walk-A blocks. **Proven by scratch test (3s timeout hang); the concurrent variant passes instantly.** This is structurally #1's MAJOR-3 one level up (at fan-in, not fan-out). Bigger buffers do NOT fix it. **→ FIX: `runStreamGraph` MUST spawn one goroutine per subtree (Copy target AND Merge source) and pull siblings CONCURRENTLY; never walk sibling subtrees sequentially on one goroutine when they may share an upstream Copy.** Executor invariant: *"any two subtrees that may share an upstream Copy broadcaster must be pulled concurrently."* Acceptance gate: a Copy→{fold,fold}→combine test with ≥(buf+2) items that HANGS under a sequential walk.
- **MAJOR (R6) — `walkChain` needs a subtree signature, not the root one.** `runStreamDAG`'s tail (streamdag.go:342-356) returns `StreamReader[O]` via `foldTail[O]`/`box[O]` — graph-output typing that is WRONG for a subtree (which must yield an intermediate `streamCarrier`). **→ `walkChain(ctx, entry streamCarrier, live *liveSet) (streamCarrier, error)`, stopping at Copy/Merge boundaries; ALL O-typed tail logic stays at the ROOT only (runs once).** Acceptance gate unchanged: linear + branch-DAG suites pass byte-identically BEFORE any graph-executor test.
- **MAJOR (R7/OQ3) — the `[]T` value-path output is unbuildable generically.** Folding a stream-path Merge to `[]T` needs a `Concatenator[T]→[]T`, but Go generics can't register one for all T (only `StreamEvent→Response` + `string→string` built-ins exist); per-T registration is a real burden, and auto-registering at build time is a global-mutation wart that interacts badly with #1's MAJOR-1 (register-after-Compile invisibility). **→ FIX: cut `[]T` value-path semantics. If Merge ships, `AddStreamMerge` is STREAM-PATH-ONLY (usable only on StreamCapable graphs, no standalone Invoke `[]T`).** Also: `elemT` is NOT preserved through `copyReader` (just `chan copyItem[any]`) → the executor must re-stamp `elemT` on each subtree's entry carrier from the node's declared T (easily-missed required step).
- **MINOR/hardening (attack 2 SOUND) — nested Copy Close is leak-free in BOTH orders** (verified); `liveSet` Close ORDER is irrelevant, but COMPLETENESS is mandatory. **→ Hard rule: the executor registers and Closes EVERY copyReader independently** (not via Merge owning its sources), so a subtree that errors before consuming its copyReader can't wedge the broadcaster.
- **MINOR (OQ2) — multiset-equivalence is necessary-but-insufficient AND schedule-dependent** (a non-deadlocking schedule could pass while another hangs). **→ Merge cross-validator (if Merge ships) = multiset equality + exact element count + per-source completeness (tag frames by source so drop-A+dup-B can't cancel) + an N=1 sequence-equality case + a high-item/small-buffer concurrency stress that would hang on the BLOCKER bug.**
- **VERIFIED sound (review had teeth):** Phase-2 Copy/Merge two-stage Close composes recursively (diamond, nested, both Close orders, mid-send) — all leak-free, src closed once; concurrent subtree walk completes while sequential deadlocks (both proven); `lookupConcat` exact/interface/ambiguity; Invoke disjointness + sorted-key value determinism (`combineAdapter`/`parallelAdapter` iterate sorted `keys`); classifier fall-through ordering (Copy/Merge not whitelisted in `buildStreamPlan` → degrade → falls to `buildStreamGraphPlan`; no misclassification into single-goroutine `runStreamDAG`).

**REVISED MVP scope (recommended): ship #2 = `AddCopy` ONLY (stream-path fan-out, 1→N full-stream), DEFER ALL Merge to #3.** Rationale: the blocker lives entirely at fan-in/diamond; Copy-only fan-out (no reconvergence) has no sequential-materialization hazard and was verified leak-clean. `AddStreamMerge`'s `[]T` value path (MAJOR-3) and the unordered/multiset weakening (MINOR-OQ2) are genuinely #3 concerns, already coupled to the deferred zip/tail-fold work. Mirrors #1 cutting the tee and #4 cutting streaming-State. **If Merge must ship in #2**, it is gated on: mandatory concurrent fan-in (BLOCKER fix) + the forced-concurrency regression gate + stream-path-only (MAJOR-3 fix) + the strengthened cross-validator. Do NOT ship Merge with §3-step-3 unamended — that wording IS the blocker.

Revised sub-tasks under the Copy-only MVP: 2a (AddCopy value node + Invoke = parallelAdapter semantics) → 2b (`buildStreamGraphPlan` classifier + StreamCapable widening + degrade safety) → 2c (`runStreamGraph` + `walkChain` subtree-signature extraction + Copy fan-out via N concurrent subtree goroutines over Phase-2 `Copy`; 3-mode leak tests + equivalence-vs-Invoke sequence equality). Merge tasks (2d/2e) move to #3.

## 0. Load-bearing code facts (verified against live source)

1. **The current branch-DAG executor is provably single-goroutine and single-live-stream.** `runStreamDAG` (streamdag.go:255) is an inline `for` walk over one dynamically-selected chain. `liveCarrier` (streamexec.go:26) documents "at most one in-flight stream carrier" and a single slot suffices. The only goroutines that ever exist are the underlying llm stream's (inside `chatModelAdapter.streamRun`, component.go:81) — no fan-out goroutine is ever spawned by the executor. This is exactly why #1 deferred the tee: a Copy broadcaster (combinators.go:103) sends each frame to ALL N consumer channels (buf=1) before advancing, so it can only make progress if all N consumers are drained **concurrently** — but the inline walk drains consumers **sequentially** (one route at a time). Sequential drain of a per-frame broadcaster = deadlock. **CONFIRMED as the central problem.**

2. **`buildStreamPlan` explicitly degrades tee and fan-in TODAY** (streamdag.go:113–124): a source port feeding >1 edge → `(nil,nil)` degrade; any `toPort != portIn` (combine fan-in) → `(nil,nil)` degrade. These are precisely the two classifications #2 must make PLAN-able instead of degrade.

3. **Phase-2 `Copy`/`Merge` are standalone `StreamReader[T]` functions, NOT nodes** (combinators.go). They are goroutine-correct, two-stage-Close, leak-tested in 3 modes (combinators_test.go). They operate on already-materialised stream values. They are NOT wired into the graph topology and the executor does not reference them.

4. **`AddParallel`/`AddCombine`/`AddBranch` are VALUE-Run adapters** (parallel.go, branch.go), in-process only (`markInProcess`). `AddParallel` emits the SAME value on every route port (parallel.go:96, no tee). `AddCombine` is a multi-input node (`inPorts`, `AddEdgeTo` on named ports, combineAdapter gathers present ports). None implements `streamNode`. So under the current whitelist (streamdag.go:79–90) parallel/combine are non-whitelisted → degrade.

5. **The carrier is type-erased** (`streamCarrier{stream StreamReader[any], elemT reflect.Type}`, stream.go:81). `anyStream[T]` erases, `adaptStream[T]`/`typedStream[T]` recover concrete T. A node-level Copy would tee a `StreamReader[any]` — `Copy[any]` instantiates fine.

6. **Stream dispatch never reaches the engine** (runnable.go:387–402): `Stream` → `runLinearStream` | `runStreamDAG` | `box(Invoke)`. Checkpoint/resume live only on `RunResumable`/`Resume` (resume.go). **Disjointness CONFIRMED** — the by-construction invariant proof from #1 holds unchanged for #2.

7. **`StreamCapable() == pipeline != nil || streamPlan != nil`** (runnable.go:67). A node-bearing streamable graph must populate `streamPlan` (or a new plan field) to be capable; otherwise it degrades — never errors (except missing-folder Compile error).

## 2. Scope / public API

Proposed exact Go signatures (mirroring `AddParallel`/`AddCombine`/`AddBranch` shape — generic over graph `GI,GO` + element types, returning `(NodeRef, error)`, latching on build error):

```go
// AddCopy adds a streaming fan-out node: its single input (value or live
// stream of T) is delivered IN FULL to every one of `targets`. On the
// stream path each target receives an independent StreamReader[T] (via the
// Phase-2 Copy tee); on Invoke it forwards the same VALUE to every target
// (parallelAdapter semantics). Registers id.<key> -> target.in edges.
// inT == outT == T. In-process only (markInProcess).
func AddCopy[GI, GO, T any](g *Graph[GI, GO], id string, targets map[string]NodeRef) (NodeRef, error)

// AddStreamMerge adds a streaming fan-in node: N upstream sources (each a
// value or live stream of the SAME element type T) are interleaved into a
// single downstream stream of T (unordered, by arrival — Phase-2 Merge
// semantics). On Invoke it gathers present sources in stable sorted-key
// order into []T (deterministic). Sources wired via AddEdgeTo on named
// ports (inPorts), like AddCombine. outT == []T  (or T if a tail folder is
// supplied — see DEFERRED). In-process only.
func AddStreamMerge[GI, GO, T any](g *Graph[GI, GO], id string, sources map[string]NodeRef) (NodeRef, error)
```

**Naming rationale (eino-informed):** eino exposes graph-level fan-out/fan-in implicitly through multi-edge wiring; flow-v2 already chose explicit node constructors (`AddParallel`/`AddCombine`/`AddBranch`). `AddCopy` mirrors the standalone `Copy` function name (consumers already know it). `AddStreamMerge` (not `AddMerge`) disambiguates from the value-`AddCombine` and signals the streaming intent + the unordered caveat.

**MVP boundary:**
- `AddCopy` (1→N full-stream fan-out) and `AddStreamMerge` (N→1 unordered interleave).
- Both work on the stream path (genuine concurrent streaming) AND degrade-cleanly to deterministic Invoke semantics.
- The new `runStreamGraph` multi-goroutine executor + `buildStreamGraphPlan` classifier.
- Reuse Phase-2 `Copy[any]`/`Merge[any]` verbatim as the goroutine engines.

**Explicit DEFERRALS:**
- **Ordered / zip merge → item #3** (gated on #2). #2 is unordered-interleave only.
- **Tail-folding Merge output to a single T** (vs `[]T`) — deferred; MVP Merge output type is `[]T` on value path and `StreamReader[T]` on stream path. (A folder-to-T is a #3 concern alongside zip.)
- **Copy of a RAW stream out-port (a chatmodel feeding 2 nodes WITHOUT an explicit `AddCopy`)** — still DEGRADES (the implicit-tee case #1 deferred). MVP requires an explicit `AddCopy` node; implicit multi-edge from a stream port stays a degrade. (This keeps the planner's tee-detection at streamdag.go:120 intact as a degrade trigger for the *non-node* case.)
- **Merge sources of DIFFERENT element types** — rejected from MVP (Merge requires homogeneous T; heterogeneous fan-in is `AddCombine`'s job, value-only).

## 3. Concurrency contract (the tee-deadlock resolution)

**Executor: `runStreamGraph(ctx, in) (StreamReader[O], error)` in a new `streamgraph.go`.**

Goroutine model:
1. The executor walks the plan from entry on the **main goroutine** up to the first Copy/Merge boundary, threading a `streamCarrier` exactly like `runStreamDAG` (fold-on-input at value nodes, re-stream at streamNodes).
2. **At a Copy node:** materialise the upstream into a `StreamReader[any]` (if the carrier is a value, `box` it; if a stream, use it directly). Call `Copy[any](src, N)` → N `copyReader`s. Spawn **N goroutines**, one per target subtree. Each goroutine: takes a child `ctx` (derived from a single `cancelCtx` the executor owns), threads its `copyReader` as the subtree's entry carrier, and walks its subtree inline (the SAME single-route walk as `runStreamDAG`, factored into a shared `walkChain` helper). Because the broadcaster (combinators.go:103) blocks until every consumer channel accepts each frame and all N subtree goroutines are concurrently pulling, **there is no deadlock** — this is exactly the "deliberate goroutine-per-consumer model" #1's MAJOR-3 prescribed.
3. **At a Merge node:** each of its N source subtrees is walked (each producing a `StreamReader[any]`); these are collected and passed to `Merge[any](srcs...)` → one interleaved reader, which becomes the downstream carrier on the continuing walk. Source subtrees that themselves contain a Copy fan-out spawn their own goroutines recursively.
4. **The tail:** the final downstream stream is materialised to `StreamReader[O]` via `foldTail`/`box` exactly as today.

**Determinism argument (value path / Invoke):** On Invoke the engine runs `runCore` (barrier scheduler) — copy/merge nodes are ordinary value-Run adapters there. `copyAdapter.Run` = `parallelAdapter.Run` (emit same value on all ports) → deterministic. `streamMergeAdapter.Run` gathers present source ports in **stable sorted-key order** → deterministic `[]T`. So **I1 byte-identical Invoke is preserved** (the value path has zero concurrency-order dependence).

**Determinism argument (stream path):** Copy fan-out is order-preserving per consumer (each `copyReader` yields the full source in order). The ONLY nondeterminism is **Merge interleave order** (arrival-dependent). This is by design (unordered) and is the reason the equivalence cross-check for Merge must be **multiset equality**, not sequence equality (Q4, R1).

**Leak contract:** The executor owns one root `cancelCtx`. A `liveSet` (replacing the single-slot `liveCarrier`) records every Copy broadcaster handle, every `copyReader`, and every Merge reader. On error return OR consumer early-Close, deferred cleanup: cancel the root ctx, then Close every recorded stream (the Phase-2 two-stage Close drains each broadcaster/puller so no goroutine blocks forever). `settleGoroutines()` is the proof.

## 4. Invariant protection (proof-by-construction)

- **I1 (byte-identical fresh Invoke):** Invoke → `r.engine.Run` → `runCore`. Copy/Merge nodes are value-Run adapters there with deterministic semantics (Q3, §3). The new streaming executor is never on the Invoke path (fact #6). Equivalence-vs-Invoke tests cross-check RESULT (multiset for Merge).
- **I2 (resume cursor integrity):** `runStreamGraph` never constructs/reads/writes a Checkpoint/EdgeFireState/Activated and never calls `r.engine.*`. Copy/Merge-bearing graphs are non-serializable (`markInProcess`) → non-checkpointable → suspend never reached. No cursor state exists to corrupt.
- **I3 (sibling-error-wins-no-checkpoint):** that ordering lives in `runCore`'s suspend splice; unreachable from the streaming path. Unreachable → unperturbable.
- **`runLinearStream` oracle preserved:** untouched. `runStreamDAG` untouched (still single-goroutine). The new executor is purely additive — a third classifier + third executor. A graph WITHOUT copy/merge nodes never enters `runStreamGraph`.
- **Equivalence-vs-Invoke as cross-validator:** mandatory per shape. For Copy-bearing graphs: full sequence equality (Copy is order-preserving). For Merge-bearing graphs: **multiset (sorted) equality** of `Stream`-concat vs `Invoke` `[]T` (the sole place the cross-check is weakened — flagged OQ-2).

## 7. Open questions for round 2 (hammer these)

1. **(BLOCKER candidate) Is the goroutine-per-subtree model leak-clean under NESTED Copy (Copy whose subtree contains another Copy)?** The broadcaster of the inner Copy is driven by a goroutine that is itself a consumer of the outer Copy's broadcaster. Two-stage Close must propagate root→leaf across the nesting. Does cancelling the root ctx + Closing outer `copyReader`s reliably drain the INNER broadcaster, or can an inner broadcaster block on a send to an inner consumer whose subtree goroutine already exited on root-cancel? **This is the #2 equivalent of #1's deadlock — verify there is no leak/deadlock in the nesting via an explicit nested-Copy 3-mode leak test, and stress whether `liveSet` ordering of Closes matters (must we Close leaf-first or root-first?).**

2. **Does multiset-only equivalence-vs-Invoke for Merge leave a class of bugs undetectable?** Specifically: a Merge that drops frames from one source but duplicates from another could pass a naive multiset check if counts coincidentally match. Is element-count + per-source-completeness enough, or do we need to tag frames by source for the test? Is unordered Merge even the right MVP default, or should #2 ship NOTHING streaming-merge and defer ALL merge to #3 (leaving #2 = Copy-only)?

3. **Is `[]T` the right Merge output type, or does the type-erased carrier + `[]T`-folder bridge (R7/Q3) introduce a folder-registration burden that breaks the "no new exported symbols needed for built-ins" expectation?** Should value-path Merge instead require a user-supplied combine (collapsing to `AddCombine`) — making `AddStreamMerge` purely a stream-path concept with NO standalone value semantics (and thus only usable on `StreamCapable` graphs)?

4. **Should `runStreamDAG` and `runStreamGraph` be unified after `walkChain` extraction, or kept as two executors?** Keeping two preserves the single-goroutine oracle-adjacent path but risks divergence; unifying risks making every branch-DAG graph pay the multi-goroutine complexity. (Round-1 leans KEEP TWO, mirroring #1's keep-`runLinearStream` decision.)

5. **Backpressure deadlock under Copy-into-Merge:** if a Copy feeds two subtrees that BOTH feed the same Merge, the Merge's two pullers pull from the two `copyReader`s; the broadcaster blocks until both `copyReader`s accept each frame; the Merge's bounded shared chan (buf=1) means a puller blocks until Next consumes. Construct the schedule and prove no deadlock (this is the diamond Copy→{A,B}→Merge — the most likely real-world shape, and the most likely place a buf-1 cycle stalls).
